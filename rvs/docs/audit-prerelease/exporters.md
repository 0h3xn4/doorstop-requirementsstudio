## Findings

### EXPORTERS-01 Short CSV rows silently blank every missing column (statements wiped)
- Where: src/rvs_core/exporters/itemsio.py:_csv_rows (lines ~157-170)
- Severity: high
- Confidence: verified
- What is wrong: a record with fewer cells than the header gets "" for the missing columns, and a present-but-empty column means "clear this field". Only rows with too MANY cells are flagged. A ragged CSV (hand-made, generated by a script, some editors drop trailing empty cells) therefore clears `text`, `owner`, etc. of existing items with no error; dry run only says "update ... owner, text, title".
- Evidence: `printf 'id,title,text,owner\nSYS-0001,New title\n' > short.csv; rvs import p short.csv` -> `row 2 update SYS-0001 owner, text, title`, then SYS-0001.yml has `text: ''`, `owner: ''`.
- Why it matters: silent loss of requirement text from an import; for non-baselined items there is no reason prompt and the dry run does not show values.
- Proposed fix: treat a record shorter than the header as a row error ("row has N cells, header has M") like the too-long case (allow only trailing empty cells when the record is exactly header length).
- Test that would catch it: read_csv/plan_import on "id,title,text\nSYS-0001,x\n" must report an error / not plan a text change.

### EXPORTERS-02 CSV import cannot read what European-locale Excel writes (semicolon, cp1252, UTF-16)
- Where: itemsio.py:read_csv (utf-8-sig decode, csv.reader default delimiter)
- Severity: high
- Confidence: verified
- What is wrong: no delimiter detection and no fallback encoding. Excel in German/French etc. locales saves "CSV" as `;`-separated cp1252 (or "CSV UTF-8" with `;`). The guide says "edit it in a spreadsheet and bring the changes back".
- Evidence: semicolon file -> `row 1 ERROR Unknown column(s): id;document;level;...;link_verifies. Use the column names of an exported file.`; cp1252 file -> `rvs import: latin1.csv could not be read ('utf-8' codec can't decode byte 0xf6 in position 393: invalid start byte)`; UTF-16 file -> same codec message. (Opening RVS's own comma CSV in such an Excel also shows one column.)
- Why it matters: the CSV round trip fails for a big part of the intended (ESA/European) user base; messages are jargon. XLSX works, but the guide presents CSV equally.
- Proposed fix: sniff delimiter from the header line (`,` `;` `\t`), try utf-8-sig then utf-16 (BOM) then cp1252 with a note; at least give a plain-language message ("save as UTF-8 comma-separated or use XLSX"); consider writing `sep=`-free semicolon export option.
- Test that would catch it: read_csv of the header joined with `;`, and of cp1252 bytes.

### EXPORTERS-03 Import apply is not atomic; message hides the partial state; blank-ID rows duplicate on re-run
- Where: itemsio.py:apply_import; rvs_cli/main.py:_import / main()
- Severity: medium (AUDIT.md lists non-transactional as known, but its claim "re-running completes it" is wrong for blank-ID rows)
- Confidence: verified
- What is wrong: creates are written first, then updates one by one. A failure mid-way leaves earlier changes in place; the CLI prints only `rvs: Operation not permitted (.../EPS-0001.yml.<pid>.<tid>.tmp)` (a temp-file name, exit 2) with no list of what was applied. Re-running the same file creates the blank-ID row again (duplicate item).
- Evidence: chattr +i on EPS/EPS-0001.yml, CSV with SYS-0001 update, EPS-0001 update, SYS-0002 update, blank-id create: result SYS-0005 created, SYS-0001 retitled, rest not; unlock, dry-run again: `1 to create, 2 to update` (the new item would be created a second time).
- Why it matters: half-imported project, duplicates when the user retries as advised.
- Proposed fix: on failure report created/updated UIDs so far; for blank-id rows consider matching an existing identical new item, or print the created UIDs on the first run so the user can fix the file; ideally snapshot/restore touched files like baseline create does.
- Test that would catch it: monkeypatch update_item to raise on the 2nd update; assert either rollback or a message naming applied rows.

### EXPORTERS-04 Import of N new items is quadratic and writes each item ~6 times
- Where: itemsio.py:apply_import -> adapter add_item/Doorstop Document.add_item (next_number scans all items); doorstop_adapter.py:403
- Severity: medium
- Confidence: verified
- What is wrong: 500 rows 6.1 s, 1000 rows 17.5 s, 3000 rows 95 s (machine loaded, ~7 load avg, but per-row cost grows with n: 12 -> 17 -> 32 ms). cProfile for 1000 rows: 6000 `Item.save` calls, 14 s in `Document.next_number` (max over all items per add). 100k-row import is not feasible; no progress output.
- Why it matters: bulk import is "the main route for bulk data" (extrapolated: 5,000 rows several minutes, 20,000 rows well over an hour).
- Proposed fix: avoid repeated saves in adapter.add_item (one write), pass `number` explicitly and avoid next_number scan, print progress.
- Test that would catch it: perf test importing 2,000 rows with a time bound.

### EXPORTERS-05 PDF silently drops every glyph the bundled fonts lack (CJK, Arabic, Hebrew, emoji; Greek in code spans)
- Where: exporters/pdf_out.py (ReportLab TTFont, no fallback or warning); fonts/*.ttf
- Severity: medium
- Confidence: verified
- What is wrong: IBM Plex Sans has 895 glyphs: no CJK/Arabic/Hebrew/emoji, no U+207B (superscript minus), U+2103 (degree Celsius), U+2610/2717; IBM Plex Mono lacks all Greek (`ΔV`, `Ω`, µ-as-U+03BC in `code` spans). They render as blank space with no warning; combining marks are drawn detached ("e´a¨"). The same text is correct in DOCX (LibreOffice check) and HTML.
- Evidence: item text "...display 日本語 中文 한국어 text." -> `pdftotext`: "The system shall display text."; picture shows blanks; `` `ΔV` `` in PDF -> "V". The test `test_pdf_handles_non_latin_text` asserts only that pages exist.
- Why it matters: reviewers/customers read PDFs; requirement text (e.g. "10 ℃", "ΔV") is altered without notice.
- Proposed fix: detect characters missing from the font (`font.face.charToGlyph`) and replace with a visible marker + add a note in the document ("N characters not available in the PDF font"); add Greek to Mono or use Sans for code spans.
- Test that would catch it: render "温度" and assert the output contains a marker/note or raises a warning.

### EXPORTERS-06 DOCX numbered lists continue across items (4, 5, 6 ...)
- Where: exporters/docx_out.py:_markdown (style "List Number")
- Severity: medium
- Confidence: verified
- What is wrong: python-docx's "List Number" style shares one numbering instance for the whole document, so every ordered list continues counting.
- Evidence: 3 items each with "1. first 2. second 3. third", `rvs export --spec -o x.docx`, LibreOffice text: SYS-0400 1-3, SYS-0401 4-6, SYS-0402 7-9.
- Why it matters: wrong numbering in a specification delivered to customers.
- Proposed fix: create a new w:num with a lvlOverride/startOverride per ordered list, or write literal "1." text.
- Test that would catch it: two spec entries with ordered lists; check numId differs or numbering restarts.

### EXPORTERS-07 Spec DOCX export aborts on a control character in item text; nothing flags the item
- Where: docx_out.py (no textcheck.clean, unlike xlsx_out/reqif); validate has no rule
- Severity: medium
- Confidence: verified
- What is wrong: an item file containing e.g. `\x01` (YAML `"\x01"`, hand edit/merge/Doorstop CLI) makes `rvs export --spec -o x.docx` fail with `All strings must be XML compatible: Unicode or ASCII, no NULL bytes or control characters` (does not name the item). `rvs validate` reports no finding; HTML/CSV write the raw control char, XLSX/ReqIF replace it.
- Evidence: SYS-0001.yml `text: "The spacecraft \x01shall\x0b provide \u0000 power"` -> spec docx fails, vcm docx works, spec html/pdf succeed.
- Proposed fix: apply textcheck.clean in the DOCX (and HTML) renderers, and add a validation finding naming the item.
- Test that would catch it: render_docx of a Doc with "\x01".

### EXPORTERS-08 Markdown subset silently flattens tables, nested lists, code blocks; continued list items lose bold
- Where: exporters/mdlite.py (parse, continuation branch `inline(plain(items[-1]) + ...)`)
- Severity: medium
- Confidence: verified
- What is wrong: in HTML/DOCX/PDF specs a Markdown table becomes `| a | b | |---|---| | 1 | 2 |` in one paragraph, a fenced block becomes `` ``<code> code block </code>`` ``, nested bullets become one flat list, `# Heading` stays literal. "- **Bold** x\n  continued" loses the bold (plain() re-parse). A wrapped line starting `+ 5 V` becomes a bullet that drops the `+`. (The module states it is a deliberate subset, but the editor's preview renders full Markdown, and requirement tables are common.)
- Evidence: python: `parse("- **Important** thing\n  continued with `code`\n- two")` -> bold lost; `parse("Para line\n+ 5 V rail")` -> Bullets "5 V rail".
- Proposed fix: state the subset in the guide/editor preview, or render tables/nested lists; keep spans when joining continuation lines.
- Test: mdlite tests for continuation formatting and `+ ` mid-paragraph.

### EXPORTERS-09 ReqIF import of foreign XHTML mangles tables and nested lists and imports script text
- Where: reqif.py:xhtml_to_markdown
- Severity: medium
- Confidence: verified
- What is wrong: table cells are concatenated with no separator (`Mass5 kg`, `ParamValue`), nested list gives `- do A- nested A1`, `<script>alert(1)</script>` text is imported as `alert(1)`, literal `*star*`/`_u_` are not escaped so they become formatting when re-exported.
- Evidence: import of a foreign-style file, then `export --items`: text `'The **system** shall:\n\n- do A- nested A1\n\n- do B\nParamValue\n\nMass5 kg\n\nLine1\nLine2 <x> *star* _u_ 1. not list\n\nalert(1)alt text'`.
- Why it matters: silent corruption of requirement text from DOORS/Polarion exports.
- Proposed fix: emit `| a | b |` rows or tab/space separators, newline before nested lists, skip script/style elements.
- Test: foreign ReqIF fixture with a table and nested list.

### EXPORTERS-10 A numeric XLSX cell loses level precision (1.10 -> 1.1, 2.0 -> 2); exports do not mark text columns as text
- Where: itemsio.py:_cell_text (float branch); xlsx_out.set_text (no number_format "@")
- Severity: medium
- Confidence: verified
- What is wrong: when a user types `1.10` into a level cell in Excel it becomes the number 1.1; RVS reads "1.1" (and `2.0` heading levels as "2"). Export writes strings but no text number format, so edited/new cells default to General. No warning.
- Evidence: workbook rows level 1.1, 1.10 (float), '1.10' (text), 2.0 -> read_xlsx levels `1.1, 1.1, 1.10, 2`; dry run plans them as level updates.
- Proposed fix: set number_format "@" on id/level (all text) cells in the items export; when a numeric cell is read in `level` or `id`, report an error/warning instead of guessing.
- Test: xlsx with float level cell -> plan error.

### EXPORTERS-11 Very long level components are corrupted by Doorstop's float parsing; item becomes unreadable
- Where: itemsio.py:_LEVEL (accepts any digits); Doorstop Level
- Severity: medium (absurd input, but import reports success and the project is then broken)
- Confidence: verified
- Evidence: `printf 'id,level\nSYS-0001,99999999999999999999.1\n'`; import prints "1 updated"; file has `level: 1.0e+20`; `rvs validate` -> `RVS-ITEM-UNREADABLE: An item file has content RVS cannot read (ValueError)` (no file named). `1234567890123456.1` -> stored `...456.0`; `3.14159265358979323846` truncated.
- Proposed fix: limit each level component (e.g. <= 6 digits) and total depth in the plan.
- Test: plan_import with such a level must return an error.

### EXPORTERS-12 Blank / duplicate columns: CSV and XLSX behave differently, last duplicate wins silently
- Where: itemsio.py:_csv_rows, read_xlsx, _canonical_header
- Severity: low
- Confidence: verified
- Evidence: CSV header `id,title,` (Excel often adds trailing comma) -> `row 1 ERROR Unknown column(s): .` (XLSX skips blank headers); header `id,title,title` with values A,B imports "B" with no warning; header `id,uid` (alias duplicate) imports the second id.
- Proposed fix: ignore empty-named columns that are blank in all rows, and report duplicate (after alias) columns as an error.

### EXPORTERS-13 Dry run does not show values; blank cells (also formulas without cached value, merged cells) are planned as "clear"
- Where: itemsio.py:plan_import; main.py:_import printing
- Severity: medium
- Confidence: verified
- What is wrong: the plan lists only field names (`update SYS-0001 text, title`), never before/after. XLSX read with data_only: a formula cell that has no cached value (files written by scripts/other tools) and merged-away cells read as blank, so title/text are planned as cleared. An unrelated dry-run can therefore hide a mass-clear.
- Evidence: `x_formula.xlsx` (`=1+1`, no cache) -> `update SYS-0001 text, title`, read values `''`; `x_merge.xlsx` (merged B2:B3) -> SYS-0002 title/text cleared.
- Proposed fix: show old -> new (truncated) in the dry run, and flag "blank cell clears an existing value" count.

### EXPORTERS-14 Output path handling: temp-file names in errors, and -o can overwrite project files
- Where: atomicio.write_bytes; rvs_cli/output.py:emit
- Severity: low
- Confidence: verified
- Evidence: `-o <dir>` -> `rvs: Is a directory (.../.dd.14813.139845576945792.tmp)`; missing parent -> `No such file or directory (.../nodir/sub/.x.csv.14828.<tid>.tmp)`; `-o ""` -> "Is a directory"; `rvs export p --vcm -o p/rvs-project.yaml` exit 0 and replaced the project file (and `-o p/EPS/EPS-0001.yml` replaced an item, project then reports RVS-ITEM-UNREADABLE).
- Proposed fix: catch OSError in write_bytes and re-raise naming the target; refuse `-o` targets inside the project that end .yml/.yaml/.jsonl.

### EXPORTERS-15 Deactivating an item by import is irreversible in RVS and breaks references silently
- Where: itemsio.py:plan_import ("inactive item" error), docs/guide/02-guided-walkthrough.md §7
- Severity: medium
- Confidence: verified
- Evidence: import `EPS-0003,no` OK; re-import `EPS-0003,yes` -> `EPS-0003 is an inactive item ... use a new ID`; afterwards `rvs validate` has `ERROR RVS-LINK-TARGET-MISSING VER-0003 ... has a 'verifies' link to EPS-0003, which does not exist`. No warning at import time that other items reference it; hint says "does not exist".
- Proposed fix: allow `active=yes` for an inactive uid; warn at plan time about inbound links; say "is inactive" in the validate message.

### EXPORTERS-16 ReqIF import: silent drops for duplicate ids, missing ids, dangling refs; case-sensitive link names
- Where: reqif.py:_read_reqif, _place
- Severity: low
- Confidence: verified
- Evidence: two SPEC-OBJECTs with same IDENTIFIER -> only 1 created, no note; objects without IDENTIFIER -> note "in no specification" (misleading), nothing imported; hierarchy ref to missing object skipped silently; relation type `Satisfies` not imported ("1 relation(s) of type 'Satisfies' were not imported") while `parent` is matched case-insensitively; enum `Draft` vs vocab `draft` is a hard error.
- Proposed fix: notes for each case; match relation names and enum labels case-insensitively.

### EXPORTERS-17 ReqIF export keeps remote images and has no size limit on import
- Where: reqif.py:_xhtml_div (scheme allow-list includes http/https for src); read_reqif/read_csv/read_xlsx (no byte limit; xlsx 400 MB)
- Severity: low
- Confidence: verified (images), reading-only (memory)
- Evidence: statement `![i](http://evil.example/p.png)` exports `<xhtml:img alt="i" src="http://evil.example/p.png" />`; other tools that render it will fetch the URL. RVS itself never fetches. javascript:/data:/file: links are stripped correctly.
- Proposed fix: drop `src` for images unless relative.

### EXPORTERS-18 Smaller items
- Dry run (and validate/export) create `.rvs-cache/` in the project when absent (verified: before/after snapshot shows 5 new files); with a warm cache nothing changes. Docs say "writes nothing". Severity low.
- CSV `_row` numbers are physical line numbers at the END of the record, not Excel row numbers (multi-line cells shift them; comment lines count). Severity low.
- Error text ends in `..` (`...terminal..`) because messages already end with "." and are wrapped with ".". Severity low.
- Empty CSV prints `Dry run: 0 to create ... 0 errors` exit 0 with no hint that the file was empty. Low.
- CSV export comment lines `# Project: <name>`: a project name containing a newline starts a new unprotected line (`=...`). Low, reading-only.
- U+0085 (NEL) in text is turned into a space/newline by YAML storage (round trip changes it). Low.
- Hidden sheets are imported; a sheet named other than a prefix with a `document`-less header gets the sheet name as document (message "belongs to document SYS, but the row says Notes"). Low.
- Password-protected/OLE2 xlsx gives "not an Excel workbook" (no hint about encryption). Low.
- Numeric/boolean XLSX cells in text columns: TRUE -> "yes". Low.
- DOCX files are ~850 KB for a 1-page document because members are stored uncompressed (zipnorm) and the default template is large. Low.

## Checked and found correct
- Formula injection: CSV (all matrix CSVs and items CSV) protects = + - @ TAB CR with reversible apostrophe; XLSX writes every cell as string, no `<f>` element in any sheet; HTML escapes everything (no script/img/a tags emitted, no external URLs, fonts inline data URIs); PDF/DOCX plain text; JSON fine; ReqIF escapes raw HTML and strips javascript:/data:/file: links.
- ReqIF safety: DOCTYPE/entity (XXE, billion laughs, external DTD) refused in all tested cases; deep hierarchy (>100) and deep XHTML give plain errors; empty/truncated/non-XML/wrong-encoding files give plain errors; latin-1 and UTF-16 with declaration are read.
- Round trips: satellite300 (339 items) via CSV, XLSX and ReqIF into an emptied project reproduce the items CSV exactly and ReqIF byte-identically; ~65 awkward strings round trip (except NEL and leading/trailing blank lines which YAML normalises); duplicate ids in a file, inactive ids, lowercase ids, ids below the highest number, wrong document, parents missing/in wrong document, `--skip-errors` not creating orphans are all reported correctly.
- Change control on import: baselined (and "part of a baseline") items need `--reason`; reasons checked before any write; unknown/closed `--cr` refused before writing; history entries carry who/why/cr.
- zip bomb (600 MB) and corrupt/empty/OLE2/macro-typed xlsx are refused with messages; 100k-row CSV dry-run in ~4 s; 20 MB cells accepted.
- Determinism: xlsx, docx, pdf, html, reqif, items outputs byte-identical across cwd, TZ, locale, PYTHONHASHSEED (user name is part of provenance by design).
- Atomic output write keeps previous file; symlink target is followed.
- Bundled fonts present; PDF embeds Plex fonts.
- DOCX/PDF/HTML handle very long unbroken strings, CJK/RTL in DOCX (LibreOffice check), 3,000-item exports in 1-6 s.

## Questions about intended behaviour
1. Should a blank cell in a present column clear a stored value on import (current behaviour)? Combined with EXPORTERS-01/13 it is risky; confirm intent.
2. Is the dry run allowed to create `.rvs-cache` in the project (documented as "writes nothing")?
3. Should `ReqIF.ForeignID` of foreign tools be kept somewhere (e.g. `ref`) for traceability back to the source tool? Today it is dropped.
4. Is `rvs export -o` into the project folder meant to be allowed (and overwrite project files)?
5. Intended behaviour for requirement tables in statements: is the Markdown subset documented anywhere for authors?
