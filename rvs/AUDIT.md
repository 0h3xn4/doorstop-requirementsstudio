## Verdict so far

**Not ready to release as it is.** There are no critical findings (nothing found that silently corrupts a baseline that was created correctly, or that makes the tools unusable for everyone), but 167 findings were recorded: 0 critical, 10 high, 93 medium, 64 low. The ones that block a release in my judgement are the **high** group and a handful of **medium** ones:

- **Untrusted project folders are not safe to open.** A project received as a zip or Git clone can make RVS (a) read an arbitrary local file into findings (`!include` guard bypass, CORE-DATA-01), (b) overwrite files outside the project through a planted symbolic link (`.rvs-cache`, CORE-DATA-03; `.rvs-cache/snapshots/<commit>`, CHANGECONTROL-01) and (c) abort the whole GUI process with no crash handler, by item text such as `![x](/dev/zero)` (GUIP-01). Spreadsheet formulas can still be injected through the CSV provenance lines (ANALYSIS-05).
- **Baselines are verified in only one place.** `rvs baseline verify` notices a moved tag or an edited manifest, but `rvs diff`, `rvs export --baseline` and the GUI diff use the forged content without a word (CHANGECONTROL-02), and the check covers item content only (CHANGECONTROL-03, 06).
- **Bulk import can silently destroy data.** A CSV row with fewer cells than the header blanks the missing columns, including the requirement text (EXPORTERS-01). CSV written by Excel in a European locale (semicolons, cp1252) cannot be read at all (EXPORTERS-02). Import is not atomic (EXPORTERS-03).
- **The GUI can lose or misapply edits.** A finished background validation overwrites a requirement edited meanwhile (GUIAPP-01); a project opened in the background switches under an open dialog and the dialog's import is applied to the wrong project (GUIAPP-02); one unreadable entry in the recent-projects list stops the application starting (GUIAPP-03); an item with a retired vocabulary value opens "modified" and the value is blanked on save (GUIP-02).
- **Legal and packaging.** The Linux bundle contains GNU Readline (GPL-3.0) in a proprietary product (RELEASE-01); the licence report and SBOM omit what the bundle contains (RELEASE-02, 03); nothing tests the built wheel (RELEASE-06).

The full test suite passes (820 passed, 6 deselected, 231 s, Linux, Python 3.13), ruff and mypy (strict) are clean, and clean installs of the wheel (Python 3.11, 3.12, 3.13) and the sdist (3.11, 3.13) work. Measured line coverage of `src/` is 93.3% and branch coverage 85.8% (GUI branches 76.0%); a full run in reversed order with a different time zone, locale and empty home directory is also green. **But the suite is a weaker safety net than its size suggests**: of 110 hand-made one-line defects injected by the test auditor, 66 left every covering test green, and many of the findings below survive deliberate mutation of the code (see the test-gap findings), which is how they got through. Two further facts: with `SOURCE_DATE_EPOCH` set in the environment (the release script exports it) two golden tests fail (TESTS-14), and some tests write outside their sandbox (`~/.config/rvs/cache.key`, `.rvs-cache` inside `examples/`; TESTS-07, 08).

A ✔ after an ID means I reproduced the finding myself after the auditor reported it. All others carry the auditor's own reproduction (commands and output are in the per-area reports, linked below) unless the report says "reading-only".

## How the audit was done

- **Scope:** everything in `rvs/` at commit `92adeeb` (branch `develop` after PR #3): library `rvs_core`, command line `rvs_cli`, window `rvs_gui`, `packaging/`, `scripts/`, `tests/`, the documentation, the CI workflows. The repository root is upstream Doorstop and was **not** audited.
- **Method:** ten independent read-only auditors, each reading every file of its slice line by line, running the code with normal, edge-case and deliberately bad inputs in scratch copies, judging the tests, and (for the test-quality and several code slices) injecting small deliberate defects into a copy of the code to see whether any test notices. Each reproduced what it reported; findings that could only be read are marked *reading-only*. I then ran the whole test suite once myself, reproduced the most serious findings, and merged the reports. Some findings were reported by several auditors; they are listed once per report here, and the themes below group them.

## Decisions needed from the owner before fixing

These change behaviour or are policy, so I will **not** decide them silently:

1. **Retiring an item.** Today `active: no` makes every link to it an error ("does not exist"), and `obsolete` requirements stay in all gap lists. Which is the supported way to retire? My proposal: links to an inactive item become a *warning that says it is inactive*; `obsolete` items drop out of gap checks (configurable).
2. **A blank CSV/XLSX cell on import.** It currently *clears* the stored value, and a short row clears its missing columns. My proposal: short rows are an error; a blank cell clears only when the column header is present and the cell exists (as now) but the dry run lists "N fields will be cleared" with before/after values. Do you want blank = "leave unchanged" instead?
3. **Should `rvs diff` / `rvs export --baseline` refuse (exit 1) or only warn** when the baseline fails its cheap integrity check? My proposal: warn on stderr, mark the output "UNVERIFIED", exit 1 for `export`.
4. **Symbolic links inside a project** (item files, `config/`, `history/`, `.rvs-cache`): refuse to write through a link that leaves the project folder? My proposal: yes, everywhere.
5. **Configuration typos** (status names in `promote_on_baseline`, `reason_required_statuses`, unknown rule parameters, link attribute names): hard error at load (my proposal) or a finding?
6. **Traceability matrix between non-adjacent documents** (`--trace MIS:EPS` flags every row as a gap): follow links through the intermediate documents, or refuse the pair?
7. **Reproducible output.** The user name is part of the provenance, so the same commit built by two accounts differs. Pin the user when `SOURCE_DATE_EPOCH` is set, or only reword the documentation?
8. **Change-request statuses** are freely settable (a closed request can be re-opened or deferred without a reason). Add allowed transitions to `changes.yaml`?
9. **Licences.** Remove Readline from the bundle (straightforward). The LGPL "relinking" statement and the proprietary `rvs/LICENSE` against Qt/PySide6 and Doorstop need your (or a lawyer's) decision: RELEASE-02, 03.
10. **Supported systems.** The wheelhouse and the glibc statement in the documentation (RHEL 8 is named, but PySide6 6.12.0 needs glibc 2.34+); macOS and Windows were not tested (only CI on Windows runs the tests).
11. **`rvs-studio <path>`** ignores its argument and `--version`/`--help` start the window: implement, or document?

## What was checked and found correct

Each report ends with the list of behaviours the auditor verified (so a clean area is not a skipped area). In short: **offline guarantee** (no network module loaded in any path tested); **formula and HTML injection in all export formats** except the CSV provenance lines (ANALYSIS-05); **ReqIF XXE and entity-expansion refusal**; **round trips** of the 339-item example through CSV, XLSX and ReqIF; **suspect-link logic**; **coverage numbers equal a hand count** for all ten example documents; **reason-for-change enforcement** on every edit path tried; **baseline name rules**, atomic creation and detection of manifest tampering by `baseline verify`; **exit codes** match the documentation for every command; **dry run writes no item file**; **determinism** across working directory, time zone, locale and hash seed (the user name aside); **clean installs** from wheel and sdist; **every command in the Getting Started and examples pages** reproduces its documented output.

## What this audit could not do

- **Windows and macOS were not run.** The PowerShell installer and the Windows build were reviewed by reading only; the Windows CI job runs the tests, nothing more. The GUI was exercised with Qt's offscreen platform, not on a screen.
- **Permission-denied cases** (read-only folders, unreadable files) were probed with dropped capabilities where possible, but the sandbox runs as root, so some are reading-only.
- **Two auditors were cut off by a usage limit and resumed**; the change-control auditor's mutation batch was invalidated by machine load (only four mutations count), and one auditor could not write its file (its report was saved from its hand-back text).
- **Timings** were taken on a shared 4-core machine under load.
- **The upstream Doorstop code** (repository root) was not audited.
- **External links** and the **rendering on github.com** were not checked.
